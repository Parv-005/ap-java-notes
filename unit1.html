Introduction to the Object-Oriented Paradigm

A programming paradigm is a style of organising programs. In procedure-oriented programming (POP), such as C, a program is a list of functions acting on shared data. As programs grow, any function can change any data, which makes bugs hard to trace and change expensive.

Object-Oriented Programming (OOP) models a program as a set of objects that interact. Each object bundles state (data, fields) and behaviour (methods), and it controls access to its own data. An object is a self-contained "thing" from the problem domain, such as a BankAccount, Student or Car.

One program that shows all four pillars together (answer for EJ26-1a / MS26-1b):

// ABSTRACTION: callers only know "an Account can deposit/withdraw/compute interest"
abstract class Account {
    // ENCAPSULATION: state is private; changed only through validated methods
    private final String accNo;
    private double balance;

    Account(String accNo, double opening) { this.accNo = accNo; this.balance = opening; }

    public double getBalance() { return balance; }
    public String getAccNo()   { return accNo; }

    public void deposit(double amt) {
        if (amt <= 0) throw new IllegalArgumentException("Amount must be positive");
        balance += amt;
    }
    public void withdraw(double amt) {
        if (amt > balance) throw new IllegalStateException("Insufficient funds");
        balance -= amt;
    }
    protected void addInterest(double amt) { balance += amt; }

    public abstract double interestRate();          // HOW is decided by subclasses
    public void applyInterest() { addInterest(balance * interestRate()); }
}

// INHERITANCE: reuse all the Account code; add only what is different
class SavingsAccount extends Account {
    SavingsAccount(String n, double b) { super(n, b); }
    @Override public double interestRate() { return 0.04; }
}
class FixedDeposit extends Account {
    FixedDeposit(String n, double b) { super(n, b); }
    @Override public double interestRate() { return 0.07; }
    @Override public void withdraw(double amt) { throw new UnsupportedOperationException("FD locked"); }
}

public class Bank {
    public static void main(String[] args) {
        // POLYMORPHISM: one reference type, many runtime behaviours
        Account[] accounts = { new SavingsAccount("S1", 1000), new FixedDeposit("F1", 1000) };
        for (Account a : accounts) {
            a.applyInterest();                         // dynamic dispatch
            System.out.println(a.getAccNo() + " → " + a.getBalance());
        }
        // accounts[0].balance = 1e9;   // compile error: encapsulation protects state
    }
}
Output
S1 → 1040.0
F1 → 1070.0

How this improves reusability, security and maintainability: new account types are added without touching Bank (open for extension). Balance rules live in one place, so a bug is fixed once. External code can't put an account into an invalid state.

Data Encapsulation PYQ MJ26-1aLab 6

Encapsulation means wrapping data (fields) and the code that works on it (methods) into one unit (a class), and restricting direct access to the data. This is also called data hiding. Outsiders talk to the object only through its public methods, called its interface.

How to achieve it in Java:

  1. Declare fields private.
  2. Provide public getter (accessor) and setter (mutator) methods only where needed.
  3. Put validation inside setters, so the object can't hold invalid state (it keeps its class invariant).

Benefits: control and validation, flexibility (internal representation can change without breaking callers), security, read-only or write-only properties, easier testing and maintenance.

Lab 6: Student with private attributes, getters and setters
public class Student {
    private int rollNo;
    private String name;
    private double cgpa;

    public Student(int rollNo, String name, double cgpa) {
        this.rollNo = rollNo;
        setName(name);          // reuse validation
        setCgpa(cgpa);
    }

    public int getRollNo()   { return rollNo; }          // read-only: no setter
    public String getName()  { return name; }
    public double getCgpa()  { return cgpa; }

    public void setName(String name) {
        if (name == null || name.isBlank()) throw new IllegalArgumentException("Name required");
        this.name = name.trim();
    }
    public void setCgpa(double cgpa) {
        if (cgpa < 0 || cgpa > 10) throw new IllegalArgumentException("CGPA must be 0-10");
        this.cgpa = cgpa;
    }

    @Override public String toString() { return rollNo + " " + name + " (" + cgpa + ")"; }

    public static void main(String[] args) {
        Student s = new Student(101, "Parv", 8.7);
        s.setCgpa(9.1);
        System.out.println(s);
        try { s.setCgpa(12); } catch (IllegalArgumentException e) { System.out.println("Rejected: " + e.getMessage()); }
        // s.cgpa = 12;  // compile error - field is private
    }
}

Rejected: CGPA must be 0-10

Modularity PYQ MS24-1aPYQ MJ26-1a

Modularity means dividing a large system into smaller, independent, self-contained parts (modules). Each module has a well-defined responsibility and interface. Each one can be designed, written, tested and changed separately.

Significance:

  • Manage complexity: you understand one module at a time (divide and conquer).
  • Parallel development: different teams build different modules.
  • Easier testing and debugging: a module can be unit-tested on its own.
  • Reusability: a well-made module (for example a logging or date utility) is reused in other projects.
  • Maintainability: changes stay inside one module.

Good modules have high cohesion (everything inside belongs together) and low coupling (few dependencies on other modules).

How it is achieved in Java/OOP (many levels):

  1. Methods: one task per method.
  2. Classes: one responsibility per class (Single Responsibility Principle), with encapsulated state.
  3. Interfaces: modules depend on contracts, not on implementations.
  4. Packages: group related classes (com.shop.payment, com.shop.inventory).
  5. Java Platform Module System (Java 9+): module-info.java with requires/exports.
// module-info.java  (Java 9+)
module com.shop.payment {
    requires com.shop.core;          // depends on
    exports com.shop.payment.api;    // only this package is visible outside
}

Code Reuse PYQ MJ26-1aPYQ ES24-1c

Code reuse means using existing, tested code to build new functionality instead of writing it again. It cuts development time and bugs, because tested code is trusted.

Mechanisms in Java:

  1. Inheritance (IS-A): a subclass reuses and extends the superclass. See Inheritance.
  2. Composition (HAS-A): a class reuses another by holding an instance of it. This is often preferred: "favour composition over inheritance".
  3. Interfaces and polymorphism: code written against an interface works with every future implementation.
  4. Generics: one List<T> works for every type.
  5. Libraries and packages: the Java API, Maven libraries.
  6. Methods: call the same method from many places.

How encapsulation, modularity and reuse improve maintainability (MJ26-1a): encapsulation keeps changes local, because internals can change without breaking callers. Modularity limits how far a change spreads and lets parts be tested separately. Reuse means a fix in one shared component helps every user, and there is less duplicated code to keep in sync.

Identifying Classes and Objects PYQ MJ26-2bPYQ EJ26-1b

A class is a blueprint or template that defines state (fields) and behaviour (methods). An object is a concrete instance of a class, with its own copy of the instance fields and stored on the heap.

The noun–verb analysis technique

  1. Write or read the problem statement.
  2. Underline the nouns: these are candidate classes or attributes.
  3. Remove duplicates, vague words, and nouns that are only simple values. Those become attributes (for example "title" is an attribute of Book).
  4. Underline the verbs: these are candidate methods (responsibilities).
  5. Find relationships: "has a" means association, aggregation or composition. "Is a" means inheritance. "Uses" means dependency.
  6. Check with CRC cards (Class–Responsibility–Collaborator).

Worked example: Library Management System

Relationships and why (EJ26-1b):

  • Library ◆— Book: composition. In this design, a Book record exists only as part of the Library catalogue. Deleting the library deletes its catalogue.
  • Book ◆— BookCopy: composition. A copy can't exist without its Book.
  • Library ◇— Member: aggregation. Members are people who exist independently. The library just keeps a list of them.
  • Member —— Loan —— BookCopy: association, through the Loan class. A member can have many loans.
  • Member, Librarian → Person: inheritance (IS-A).
  • Librarian - - > Loan: dependency. issue() creates or uses a Loan only inside the method.

import java.time.LocalDate;
import java.util.*;

abstract class Person {
    protected final int id; protected final String name;
    Person(int id, String name) { this.id = id; this.name = name; }
}
class Book {
    final String isbn, title, author;
    private final List<BookCopy> copies = new ArrayList<>();        // composition
    Book(String isbn, String title, String author, int nCopies) {
        this.isbn = isbn; this.title = title; this.author = author;
        for (int i = 1; i <= nCopies; i++) copies.add(new BookCopy(isbn + "-" + i, this));
    }
    Optional<BookCopy> anyAvailable() { return copies.stream().filter(BookCopy::isAvailable).findFirst(); }
}
class BookCopy {
    final String copyId; final Book book; boolean onLoan;
    BookCopy(String id, Book b) { copyId = id; book = b; }
    boolean isAvailable() { return !onLoan; }
}
class Loan {
    final BookCopy copy; final Member member; final LocalDate issued, due;
    Loan(BookCopy c, Member m) { copy = c; member = m; issued = LocalDate.now(); due = issued.plusDays(14); }
    boolean isOverdue(LocalDate today) { return today.isAfter(due); }
}
class Member extends Person {
    final List<Loan> loans = new ArrayList<>();                     // association
    Member(int id, String name) { super(id, name); }
}
class Librarian extends Person {
    Librarian(int id, String name) { super(id, name); }
    Loan issue(Book b, Member m) {                                  // dependency on Loan
        BookCopy c = b.anyAvailable().orElseThrow(() -> new IllegalStateException("No copy free"));
        c.onLoan = true;
        Loan loan = new Loan(c, m);
        m.loans.add(loan);
        return loan;
    }
}
public class LibraryApp {
    public static void main(String[] args) {
        Book b = new Book("978-0134685991", "Effective Java", "Bloch", 2);
        Member m = new Member(1, "Asha");
        Librarian lib = new Librarian(100, "Mr. Rao");
        Loan l = lib.issue(b, m);
        System.out.println(m.name + " borrowed " + l.copy.copyId + " due " + l.due);
    }
}

Constructors PYQ MS24-3aPYQ MS26-1a

A constructor is a special block that initialises a new object. It runs automatically when you use new.

  • Same name as the class, no return type (not even void).
  • Called once per object creation. It can't be static, final or abstract.
  • If you write no constructor, the compiler adds a default no-arg constructor. If you write any constructor, the default one is not added.
  • Types: default / no-arg, parameterised, copy constructor (by convention, since Java has no built-in copy constructor).
  • Constructor overloading: several constructors with different parameter lists. this(...) chains them to avoid duplicated code.
Lab 3: class Car with model, year, price (with constructor overloading)
public class Car {
    // instance variables
    private String model;
    private int year;
    private double price;
    private static int carsBuilt = 0;            // class variable shared by all cars

    // 1. default (no-arg) constructor
    public Car() {
        this("Unknown", 2024, 0.0);              // chain to the parameterised one
    }
    // 2. parameterised constructor
    public Car(String model, int year, double price) {
        this.model = model;
        this.year = year;
        this.price = price;
        carsBuilt++;
    }
    // 3. overloaded: model only
    public Car(String model) { this(model, 2024, 500000); }
    // 4. copy constructor
    public Car(Car other) { this(other.model, other.year, other.price); }

    public void display() { System.out.printf("%-10s %d  ₹%,.0f%n", model, year, price); }
    public static int getCarsBuilt() { return carsBuilt; }

    public static void main(String[] args) {
        Car c1 = new Car();                              // default
        Car c2 = new Car("Nexon", 2023, 950000);         // parameterised
        Car c3 = new Car("Swift");                       // overloaded
        Car c4 = new Car(c2);                            // copy
        c1.display(); c2.display(); c3.display(); c4.display();
        System.out.println("Cars built: " + Car.getCarsBuilt());
    }
}
Output
Unknown    2024  ₹0
Nexon      2023  ₹950,000
Swift      2024  ₹500,000
Nexon      2023  ₹950,000
Cars built: 4

Output explained: the compiler picks a constructor by matching the number and types of arguments (compile-time polymorphism). Each this(...) call ends in the 3-argument constructor, so carsBuilt rises by exactly one per object.

Variable reassignment and references

A variable of class type holds a reference (an arrow) to an object, not the object itself. Assigning one reference variable to another copies the arrow, so both now point to the same object (aliasing). Reassigning a variable makes it point elsewhere. If no variable points to the old object any more, it becomes garbage.

Car a = new Car("City", 2020, 1e6);
Car b = a;               // aliasing: a and b → same object
b.setPrice(9e5);         // visible through a as well
a = new Car("Verna");    // a now points to a new object; b still → "City"
b = null;                // "City" object is unreachable → eligible for GC

int x = 5; int y = x; y = 10;  // primitives: y is an independent copy, x stays 5
After Car b = a; After a = new Car("Verna"); a ──┐ a ──▶ [Verna] ├──▶ [City] b ──▶ [City] b ──┘

final Car c = new Car(); means the reference can't be reassigned. The object itself can still change.

Class Relationships PYQ MS24-1bPYQ MJ26-1bPYQ MS26-2aPYQ EJ26-1b

Objects rarely work alone. UML defines how classes relate. From the weakest link to the strongest:

Dependency < Association < Aggregation < Composition (< Inheritance) "uses-a" "knows-a" "has-a" (weak) "owns-a"/part-of (strong) - - - - -> ──────────> ◇──────────> ◆──────────> ──────▷

Dependency ("uses-a")

Class A depends on class B if A uses B only temporarily: as a method parameter, a local variable, or a call to B's static method. A doesn't store B as a field. If B changes, A may have to change. It is the weakest relationship.

class Printer { void print(String s) { System.out.println(s); } }
class Report {
    void generate(Printer p) {   // dependency: Printer is only a parameter
        p.print("Report body");
    }
}

Association ("knows-a" / "has-a")

A structural link where one class keeps a reference to another as a field, so the link lasts beyond a single call. It can be one-way or two-way, with multiplicity (1–1, 1–*, *–*). Both objects have independent lifecycles, and neither owns the other.

class Teacher { String name; Teacher(String n){name=n;} }
class Student {
    String name;
    List<Teacher> teachers = new ArrayList<>();   // association (many-to-many)
    Student(String n){name=n;}
}

Aggregation is a special kind of association: a whole–part relation where the part can exist without the whole (weak ownership). The parts are usually created outside and passed in.

class Department {
    private final List<Professor> profs;
    Department(List<Professor> profs) { this.profs = profs; }   // created outside → aggregation
}
// deleting the Department does NOT delete the Professors

Composition ("owns-a" / "part-of")

A strong whole–part relationship. The part can't exist without the whole, and the whole creates and destroys its parts, so the part's lifecycle is tied to the owner. A part belongs to only one whole at a time.

class Engine { void start(){ System.out.println("Engine on"); } }
class Car {
    private final Engine engine = new Engine();   // created inside, never shared → composition
    void drive() { engine.start(); }
}
// when the Car object is garbage collected, its Engine goes too

How they are interrelated (MS24-1b): they are degrees of the same idea, one class collaborating with another. Interfaces PYQ MS24-3bPYQ ES25-1bPYQ MS26-2bLab 7

An interface is a contract: a named set of method signatures (what to do) without saying how. A class that implements the interface promises to give bodies for all its abstract methods.

public interface Shape {
    double PI = 3.14159;               // implicitly public static final (constant)
    double area();                      // implicitly public abstract
    double perimeter();

    default String describe() {         // Java 8: default method (has a body)
        return getClass().getSimpleName() + " area=" + String.format("%.2f", area());
    }
    static Shape unitSquare() {         // Java 8: static method
        return new Square(1);
    }
    private void helper() {}            // Java 9: private method (used by default methods)
}

Rules: fields are always public static final. Abstract methods are public abstract. An interface can't be instantiated and has no constructors. A class can implement many interfaces. An interface can extend many interfaces.

Significance of interfaces (MS24-3b):

  1. Full abstraction: it separates specification from implementation.
  2. Multiple inheritance of type: a class can be a Runnable, Comparable and Serializable all at once.
  3. Loose coupling: code depends on List, not ArrayList, so implementations can be swapped.
  4. Polymorphism: unrelated classes can be treated the same way.
  5. Callbacks and events: EventHandler, Runnable, Comparator.
  6. Easier testing: real objects can be replaced with mocks.

Multiple inheritance using interfaces PYQ MS26-2b

Java does not allow a class to extends two classes. If both had a method m() with different bodies, the subclass wouldn't know which to inherit. This is the diamond problem. Interfaces originally had no bodies, so implementing several of them was always safe. With Java 8 default methods, a clash is still allowed, but the class must override the method and may pick a version with X.super.m().

interface Flyable {
    void fly();
    default void info() { System.out.println("I can fly"); }
    static int maxAltitude() { return 10000; }        // called as Flyable.maxAltitude()
}
interface Swimmable {
    void swim();
    default void info() { System.out.println("I can swim"); }
}
class Duck implements Flyable, Swimmable {             // multiple inheritance of type
    public void fly()  { System.out.println("Duck flies"); }
    public void swim() { System.out.println("Duck swims"); }
    @Override public void info() {                     // MUST resolve the default-method clash
        Flyable.super.info();
        Swimmable.super.info();
    }
}
public class MultiDemo {
    public static void main(String[] args) {
        Duck d = new Duck();
        d.fly(); d.swim(); d.info();
        System.out.println("Max altitude: " + Flyable.maxAltitude());
        Flyable f = d; Swimmable s = d;              // same object seen through two types
    }
}
Output
Duck flies
Duck swims
I can fly
I can swim
Max altitude: 10000

Default methods let an interface gain new methods without breaking existing implementations. That is how List.sort() and Collection.stream() were added in Java 8. Static methods are utility methods that belong to the interface. They aren't inherited, so you call them as Interface.method().

Functional interface: an interface with exactly one abstract method (Runnable, Comparator, Callable). It can be implemented with a lambda: Runnable r = () -> System.out.println("hi");

Marker interface: an interface with no methods, used only to tag a class: Serializable, Cloneable.

Similarities between interfaces and classes (ES25-1b)

  • Both are reference types, compiled to .class files, and can be put in packages.
  • Both can contain constants, static methods, and (since Java 8) concrete methods.
  • Both can be used as the type of a variable, parameter or return value.
  • Both support inheritance hierarchies (extends), and both can be generic.

Differences: an interface can't be instantiated, has no constructors or instance fields (only constants), its methods are public by default, and a class can implement many of them.

Polymorphism using Interfaces PYQ MJ26-3b

A reference of an interface type can point to an object of any class that implements it. Calling a method through that reference runs the implementing class's version, chosen at runtime. This is runtime polymorphism with no inheritance between the classes at all.

interface Vehicle {
    void start();
    int wheels();
    default String fare(int km) { return "₹" + km * ratePerKm(); }
    double ratePerKm();
}
class Car implements Vehicle {
    public void start()       { System.out.println("Car: push-button start"); }
    public int wheels()       { return 4; }
    public double ratePerKm() { return 12; }
}
class Bike implements Vehicle {
    public void start()       { System.out.println("Bike: kick start"); }
    public int wheels()       { return 2; }
    public double ratePerKm() { return 6; }
}
class Bus implements Vehicle {
    public void start()       { System.out.println("Bus: diesel engine cranks"); }
    public int wheels()       { return 6; }
    public double ratePerKm() { return 2; }
}
public class VehicleDemo {
    static void trip(Vehicle v, int km) {          // works for ANY Vehicle, present or future
        v.start();
        System.out.println("  wheels=" + v.wheels() + ", fare for " + km + "km = " + v.fare(km));
    }
    public static void main(String[] args) {
        List<Vehicle> fleet = List.of(new Car(), new Bike(), new Bus());
        for (Vehicle v : fleet) trip(v, 10);       // same call, different behaviour
    }
}
Output
Car: push-button start
  wheels=4, fare for 10km = ₹120.0
Bike: kick start
  wheels=2, fare for 10km = ₹60.0
Bus: diesel engine cranks
  wheels=6, fare for 10km = ₹20.0

Adding Truck implements Vehicle later needs no change to trip(). This is the Open/Closed Principle.

Inheritance PYQ ES24-1cPYQ ES25-2bPYQ MS25-3bPYQ MS24-2bLab 4

Inheritance is the mechanism by which a class (subclass / child / derived) acquires the fields and methods of another class (superclass / parent / base) using extends. It models an IS-A relationship: a Dog is an Animal.

What is inherited: public and protected members (and package-private ones within the same package). Not inherited: private members (they exist in the object but can't be accessed directly) and constructors.

How it helps create new classes quickly and promotes reuse (ES25-2b, ES24-1c): the subclass gets all the tested parent code for free. It only writes what's new (extension) or different (overriding). Common code lives in one place, and polymorphic code written for the parent works for every child.

Lab 4: Animal → Dog, Cat
class Animal {
    protected String name;
    protected int age;

    Animal(String name, int age) { this.name = name; this.age = age; }

    void eat()   { System.out.println(name + " is eating"); }
    void sleep() { System.out.println(name + " is sleeping"); }
    void sound() { System.out.println(name + " makes a sound"); }
}

class Dog extends Animal {
    private String breed;                          // extension: new field
    Dog(String name, int age, String breed) {
        super(name, age);                          // reuse parent constructor
        this.breed = breed;
    }
    @Override void sound() { System.out.println(name + " barks: Woof!"); }   // overriding
    void fetch() { System.out.println(name + " the " + breed + " fetches the ball"); } // new method
}

class Cat extends Animal {
    Cat(String name, int age) { super(name, age); }
    @Override void sound() { System.out.println(name + " meows: Meow!"); }
    void climb() { System.out.println(name + " climbs a tree"); }
}

public class Zoo {
    public static void main(String[] args) {
        Dog d = new Dog("Bruno", 3, "Labrador");
        Cat c = new Cat("Kitty", 2);
        d.eat();  d.sound(); d.fetch();      // eat() inherited, sound() overridden
        c.sleep(); c.sound(); c.climb();

        Animal a = new Dog("Rex", 5, "Beagle");  // upcasting
        a.sound();                               // Rex barks (runtime polymorphism)
        // a.fetch();                            // compile error - Animal has no fetch()
        if (a instanceof Dog dog) dog.fetch();   // downcast with pattern matching (Java 16+)
    }
}

// Single
class A { void a(){ System.out.println("A"); } }
class B extends A { void b(){ System.out.println("B"); } }

// Multilevel:  Grandparent → Parent → Child  (a chain)
class Vehicle         { void move()  { System.out.println("moving"); } }
class Car extends Vehicle  { void drive() { System.out.println("driving"); } }
class SportsCar extends Car { void turbo() { System.out.println("turbo!"); } }

// Hierarchical: one parent, many children (siblings)
class Shape { void draw(){ System.out.println("shape"); } }
class Circle extends Shape { @Override void draw(){ System.out.println("circle"); } }
class Square extends Shape { @Override void draw(){ System.out.println("square"); } }

// Multiple via interfaces
interface Printable { void print(); }
interface Scannable { void scan(); }
class AllInOne implements Printable, Scannable {
    public void print(){ System.out.println("print"); }
    public void scan() { System.out.println("scan"); }
}

public class InheritanceTypes {
    public static void main(String[] args) {
        SportsCar s = new SportsCar();
        s.move(); s.drive(); s.turbo();         // multilevel: has ALL ancestors' methods
        new Circle().draw(); new Square().draw();  // hierarchical: siblings share the parent
        // Circle and Square do NOT know each other's methods
    }
}

The super keyword PYQ MS26-3a

  1. super(args): calls the parent constructor. It must be the first statement in the child's constructor.
  2. super.method(): calls the parent's version of an overridden method.
  3. super.field: accesses a parent field hidden by a child field with the same name.
class Parent { String name = "parent"; void show(){ System.out.println("Parent.show"); } }
class Child extends Parent {
    String name = "child";                       // hides Parent.name
    @Override void show() {
        super.show();                            // reuse parent behaviour
        System.out.println("Child.show; super.name=" + super.name + ", name=" + name);
    }
}

The final keyword

  • final variable: a constant that can be assigned only once.
  • final method: can't be overridden.
  • final class: can't be extended (String, Integer).
Composition vs inheritanceUse inheritance only for a real IS-A relationship where the subclass can stand in everywhere the parent is expected (the Liskov Substitution Principle). Otherwise use composition. It is more flexible, can change at runtime, and doesn't expose the parent's internals.
