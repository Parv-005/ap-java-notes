Race Conditions PYQ ES25-5aPYQ EJ26-5aPYQ ES24-5c

A race condition happens when two or more threads access shared mutable data at the same time, at least one of them writes, and the final result depends on the unpredictable timing (interleaving) of the threads. The code containing the shared access is called the critical section.

Why count++ isn't safe: it looks like one operation, but it is three: read count → add 1 → write back (read-modify-write). Two threads can interleave like this:

class Counter {
    private int count = 0;
    void increment() { count++; }          // NOT atomic → race condition
    int get() { return count; }
}
public class RaceDemo {
    public static void main(String[] args) throws InterruptedException {
        Counter c = new Counter();
        Runnable job = () -> { for (int i = 0; i < 100_000; i++) c.increment(); };
        Thread t1 = new Thread(job), t2 = new Thread(job);
        t1.start(); t2.start(); t1.join(); t2.join();
        System.out.println("Expected 200000, got " + c.get());
    }
}
Output
Expected 200000, got 137512      ← different on every run

Other forms: check-then-act (if (!map.containsKey(k)) map.put(k, v);), lazy initialisation (if (instance == null) instance = new X();), and iterating a collection while another thread modifies it.

Mutual Exclusion and Synchronization PYQ ES24-5aPYQ ES25-5aLab 12

Mutual exclusion (mutex) guarantees that at most one thread at a time runs a critical section on the same shared resource. Synchronization is the general term for coordinating threads: mutual exclusion plus ordering and visibility (making one thread's writes visible to others) and cooperation (wait/notify).

Ways to get it in Java: ① synchronized methods ② synchronized blocks ③ static synchronized methods (class-level lock) ④ explicit locks: ReentrantLock, ReadWriteLock ⑤ atomic variables (AtomicInteger, which uses lock-free CAS) ⑥ concurrent collections (ConcurrentHashMap, BlockingQueue) ⑦ immutability and thread confinement (avoid sharing altogether).

Monitor locks (intrinsic locks) PYQ ES24-5c

Every Java object has an associated monitor, also called the intrinsic lock or monitor lock. A monitor provides:

  • Mutual exclusion: only one thread can own the monitor at a time.
  • An entry set: threads trying to enter wait here in the BLOCKED state.
  • A wait set: threads that called wait() on the object sleep here (WAITING) until notified.

How it works: when a thread reaches a synchronized method or block, it tries to acquire the monitor of the lock object. If the monitor is free, the thread takes it and continues. If another thread owns it, the thread blocks. When the owner leaves the synchronized region, normally or through an exception, it releases the monitor automatically and a blocked thread can get it. Intrinsic locks are reentrant: a thread that already owns a lock can enter it again (a count is kept), so a synchronized method can call another synchronized method on the same object. Releasing the lock also flushes writes to main memory, and acquiring it refreshes the thread's view. That is the visibility guarantee (happens-before).

Lab 12 (part 1) / EJ26-5a: eliminating the race with synchronized
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantLock;

class SafeCounter {
    private int count = 0;

    // 1. synchronized METHOD - locks 'this'
    public synchronized void incMethod() { count++; }

    // 2. synchronized BLOCK - lock only the critical section
    public void incBlock() {
        // non-critical work could go here, outside the lock
        synchronized (this) { count++; }   // MUST be the same lock as incMethod (this)!
    }
    public synchronized int get() { return count; }
}

class LockCounter {                                  // 3. explicit ReentrantLock
    private int count = 0;
    private final ReentrantLock lock = new ReentrantLock();
    void inc() {
        lock.lock();
        try { count++; } finally { lock.unlock(); }  // ALWAYS unlock in finally
    }
    int get() { return count; }
}

public class SyncDemo {
    public static void main(String[] args) throws InterruptedException {
        SafeCounter sc = new SafeCounter();
        AtomicInteger atomic = new AtomicInteger();   // 4. lock-free atomic
        LockCounter lc = new LockCounter();

        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) {
                sc.incMethod(); sc.incBlock(); atomic.incrementAndGet(); lc.inc();
            }
        };
        Thread[] ts = new Thread[4];
        for (int i = 0; i < 4; i++) { ts[i] = new Thread(job); ts[i].start(); }
        for (Thread t : ts) t.join();
        System.out.println("synchronized: " + sc.get());   // 800000 (both methods)
        System.out.println("atomic:       " + atomic.get());// 400000
        System.out.println("ReentrantLock:" + lc.get());    // 400000
    }
}

Classic mistake (I verified it by running this)If incBlock used synchronized (someOtherObject) while incMethod locks this, both would still modify count under different locks. That is still a race, and the result came out as 779120 instead of 800000. All code that touches the same shared data must use the same lock.

synchronized vs ReentrantLock: ReentrantLock adds tryLock() (with timeout), interruptible locking, a fairness option, and several Conditions. But you must unlock manually. synchronized is simpler and releases automatically.

Inter-thread communication: wait(), notify(), notifyAll() PYQ ES25-5cLab 12

These are methods of Object, used so threads can cooperate instead of busy-waiting:

  • wait(): the current thread releases the monitor and goes into the wait set until notified (or interrupted, or a timeout with wait(ms)). It must re-acquire the lock before it continues.
  • notify(): wakes one arbitrary thread waiting on that object's monitor.
  • notifyAll(): wakes all waiting threads. They then compete for the lock. This is safer when there are several conditions.

Rules: ① call them only while holding the object's lock (inside synchronized(obj)), otherwise you get IllegalMonitorStateException ② always call wait() inside a while loop that re-checks the condition, because of spurious wakeups and because another thread may have changed the state first ③ notify() doesn't release the lock immediately. It is released when the notifier leaves the synchronized block.

public class OddEven {
    private int n = 1;
    private final int MAX = 10;

    synchronized void print(boolean odd) throws InterruptedException {
        while (n <= MAX) {
            while ((n % 2 == 1) != odd) {         // not my turn → wait (in a loop!)
                wait();
                if (n > MAX) return;
            }
            System.out.println(Thread.currentThread().getName() + ": " + n++);
            notifyAll();                         // wake the other thread
        }
    }
    public static void main(String[] args) {
        OddEven p = new OddEven();
        new Thread(() -> { try { p.print(true);  } catch (InterruptedException e) {} }, "Odd ").start();
        new Thread(() -> { try { p.print(false); } catch (InterruptedException e) {} }, "Even").start();
    }
}

Deadlocks PYQ ES25-5b

A deadlock is when two or more threads are blocked forever, each waiting for a resource (lock) held by another thread in the group. None can go on, so the program hangs.

The four necessary conditions (Coffman conditions)

A deadlock can happen only if all four hold at the same time:

  1. Mutual exclusion: at least one resource can't be shared (only one thread can hold it).
  2. Hold and wait: a thread holds at least one resource while waiting for another.
  3. No preemption: a resource can't be taken away by force. It is released only voluntarily.
  4. Circular wait: a cycle T1 → T2 → … → Tn → T1, where each waits for a resource held by the next.
public class DeadlockDemo {
    static final Object A = new Object(), B = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (A) {
                System.out.println("T1 locked A");
                sleep(100);
                synchronized (B) { System.out.println("T1 locked B"); }   // waits for T2's B
            }
        });
        Thread t2 = new Thread(() -> {
            synchronized (B) {                                             // opposite order!
                System.out.println("T2 locked B");
                sleep(100);
                synchronized (A) { System.out.println("T2 locked A"); }   // waits for T1's A
            }
        });
        t1.start(); t2.start();      // prints "T1 locked A", "T2 locked B", then hangs forever
    }
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) {} }
}

Prevention: break at least one condition

  • Lock ordering (breaks circular wait): every thread acquires locks in the same global order, for example always A then B. This is the most common fix. In the demo, make T2 lock A first.
  • Timeouts (breaks hold-and-wait / no-preemption): if (lock.tryLock(1, SECONDS)), and back off on failure.
  • Acquire all locks at once, or use a single coarser lock.
  • Keep synchronized blocks small, and don't call unknown ("alien") methods while holding a lock.
  • Use higher-level concurrency tools (BlockingQueue, ConcurrentHashMap).
  • Detection: jstack <pid> or a thread dump reports "Found one Java-level deadlock". ThreadMXBean.findDeadlockedThreads() does the same in code.

Related liveness problems: starvation (a thread never gets CPU time or a lock), livelock (threads keep reacting to each other and make no progress).

Java Memory Model (JMM)

Modern CPUs have per-core caches and registers, and both the compiler and the CPU reorder instructions for speed. Without rules, a write by one thread might never become visible to another, or might appear in a different order. The Java Memory Model (JSR-133, Java 5) defines when one thread's writes are guaranteed to be visible to another thread and which reorderings are allowed.

Three problems the JMM addresses: atomicity (an operation can't be seen half-done), visibility (writes are seen by other threads), and ordering (the order operations appear to happen in).

Happens-before relationship

If action X happens-before Y, then X's effects are visible to Y. The key rules:

  • Program order: each action in a thread happens-before later actions in the same thread.
  • Monitor lock: unlocking a monitor happens-before every later lock of the same monitor.
  • Volatile: a write to a volatile field happens-before every later read of it.
  • Thread start: t.start() happens-before every action in t.
  • Thread join: every action in t happens-before another thread returns from t.join().
  • Transitivity: A hb B and B hb C ⇒ A hb C.
  • Final fields: correctly constructed objects' final fields are visible without synchronization.

Memory barriers and unsafe publication

  • Memory barrier (fence): an instruction that stops the compiler and CPU from reordering memory operations across it. An acquire barrier keeps later reads/writes from moving before it. A release barrier makes earlier writes visible before later ones. The JVM inserts them for synchronized, volatile and final.
  • Unsafe publication: making an object visible to other threads without synchronization, e.g. sharedObject = new SomeObject(); in a plain field. Another thread may see the reference before the constructor's writes (a half-built object).
  • Safe publication: publish via a volatile field, a lock, a concurrent collection, or make the object immutable. Final fields are visible once the constructor finishes.
  • Best practices: volatile for visibility only, synchronized for atomicity, prefer AtomicInteger/AtomicReference, avoid unsafe publication.

volatile

A volatile variable is always read from and written to main memory, and accesses to it aren't reordered. It guarantees visibility and ordering but NOT atomicity: volatile int c; c++ is still a race. Use it for flags and one-writer status variables.

public class VisibilityDemo {
    private static volatile boolean running = true;   // remove 'volatile' → loop may never stop

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long spins = 0;
            while (running) spins++;                  // reads the flag every time
            System.out.println("Stopped after " + spins + " spins");
        });
        worker.start();
        Thread.sleep(500);
        running = false;                              // the volatile write is visible to worker
        worker.join();
    }
}

Double-checked locking for Singleton needs volatile (see Singleton). Without it, another thread could see a reference to a partially constructed object, because the writes can be reordered.

Producer-Consumer Application PYQ ES24-5bPYQ ES25-5cPYQ EJ26-5bLab 15

The producer–consumer problem (bounded-buffer problem) is a classic synchronization problem. Producer threads create data items and put them into a shared buffer of fixed capacity. Consumer threads take items out and process them. Requirements:

  1. The producer must wait when the buffer is full.
  2. The consumer must wait when the buffer is empty.
  3. Only one thread may change the buffer at a time (mutual exclusion).
  4. A waiting thread must be woken when the condition changes (signalling), without busy-waiting.

Real-world uses: print spoolers, task/job queues, logging frameworks, message brokers (Kafka), video streaming buffers, and the thread-pool work queue itself.

Solution 1: wait() and notifyAll() PYQ ES25-5c

import java.util.LinkedList;
import java.util.Queue;

class BoundedBuffer {
    private final Queue<Integer> queue = new LinkedList<>();
    private final int capacity;
    BoundedBuffer(int capacity) { this.capacity = capacity; }

    public synchronized void put(int item) throws InterruptedException {
        while (queue.size() == capacity) {           // while, not if (spurious wakeups)
            System.out.println("  Buffer FULL - producer waits");
            wait();                                  // release lock and sleep
        }
        queue.add(item);
        System.out.println("Produced " + item + "  buffer=" + queue);
        notifyAll();                                 // wake consumers waiting on 'empty'
    }

    public synchronized int take() throws InterruptedException {
        while (queue.isEmpty()) {
            System.out.println("  Buffer EMPTY - consumer waits");
            wait();
        }
        int item = queue.poll();
        System.out.println("Consumed " + item + "  buffer=" + queue);
        notifyAll();                                 // wake producers waiting on 'full'
        return item;
    }
}

public class ProducerConsumer {
    public static void main(String[] args) {
        BoundedBuffer buf = new BoundedBuffer(3);

        Thread producer = new Thread(() -> {
            try { for (int i = 1; i <= 8; i++) { buf.put(i); Thread.sleep(50); } }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "Producer");

        Thread consumer = new Thread(() -> {
            try { for (int i = 1; i <= 8; i++) { buf.take(); Thread.sleep(150); } }  // slower
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "Consumer");

        producer.start(); consumer.start();
    }
}

Role of wait() and notify() here (ES25-5c): wait() lets a thread that can't proceed (buffer full or empty) give up the lock and sleep without using CPU, so the other side can make progress. notifyAll() tells waiting threads the buffer state changed so they can re-check their condition. The while loop guarantees the condition really holds after waking. notifyAll is used instead of notify because producers and consumers wait on the same monitor, and notify could wake the wrong kind of thread.

Solution 2: BlockingQueue (recommended) PYQ EJ26-5b

java.util.concurrent.BlockingQueue does all the synchronization internally. put() blocks when the queue is full, and take() blocks when it is empty. Implementations: ArrayBlockingQueue (bounded), LinkedBlockingQueue, PriorityBlockingQueue, SynchronousQueue.

import java.util.concurrent.*;

public class PCBlockingQueue {
    private static final int POISON = -1;                      // sentinel to stop consumers

    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> q = new ArrayBlockingQueue<>(5);
        int consumers = 2;

        Runnable producer = () -> {
            try {
                for (int i = 1; i <= 10; i++) {
                    q.put(i);                                  // blocks if full
                    System.out.println(Thread.currentThread().getName() + " produced " + i);
                }
                for (int i = 0; i < consumers; i++) q.put(POISON);  // one pill per consumer
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };
        Runnable consumer = () -> {
            try {
                while (true) {
                    int item = q.take();                       // blocks if empty
                    if (item == POISON) break;
                    System.out.println("    " + Thread.currentThread().getName() + " consumed " + item);
                    Thread.sleep(100);                         // simulate processing
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };

        ExecutorService pool = Executors.newFixedThreadPool(3);
        pool.submit(producer);
        for (int i = 0; i < consumers; i++) pool.submit(consumer);
        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
        System.out.println("All done");
    }
}

Best practices: prefer BlockingQueue over hand-written wait/notify, handle InterruptedException (restore the flag with Thread.currentThread().interrupt() or check isInterrupted()), and shut down gracefully (poison pill or shutdown()). SynchronousQueue has zero capacity: every put waits for a take.

Solution 3: ReentrantLock with two Condition objects (notFull, notEmpty) lets you signal exactly the right group. You can also use two semaphores (empty slots / full slots) plus a mutex.

Introduction to Design Patterns PYQ ES24-5bPYQ EJ26-5cLab 14

A design pattern is a general, reusable solution to a commonly occurring problem in software design. It is a template or best practice, not finished code. The classic catalogue is the Gang of Four (GoF) book (Gamma, Helm, Johnson, Vlissides, 1994), with 23 patterns in 3 categories. Every pattern has a name, a problem, a solution and consequences.

Role and importance of design patterns in Java (ES24-5b):

  • Proven, tested solutions, so you don't reinvent them.
  • A shared vocabulary: "use a Strategy here" says a lot in three words.
  • They encourage OOP principles: program to an interface, favour composition, loose coupling, Open/Closed.
  • More maintainable, flexible and reusable code.
  • They are used throughout the JDK: Iterator, Runtime.getRuntime() (Singleton), Integer.valueOf (Flyweight), Arrays.asList (Adapter), Comparator (Strategy), java.io streams (Decorator), Calendar.getInstance() (Factory), JavaFX listeners (Observer).

Creational Patterns

Singleton Lab 14

Intent: make sure a class has only one instance and give a global access point to it.
Real-world uses: configuration manager, logger, database connection pool, cache, Runtime.getRuntime(), the printer spooler of an OS.
How: a private constructor, a private static instance, and a public static getInstance().

// 1. Eager initialization - simple, thread-safe, created even if never used
class EagerConfig {
    private static final EagerConfig INSTANCE = new EagerConfig();
    private EagerConfig() {}
    public static EagerConfig getInstance() { return INSTANCE; }
}

// 2. Lazy + thread-safe with double-checked locking (needs volatile - see JMM)
class Logger {
    private static volatile Logger instance;
    private int count = 0;
    private Logger() { System.out.println("Logger created"); }

    public static Logger getInstance() {
        if (instance == null) {                       // 1st check, no locking (fast path)
            synchronized (Logger.class) {
                if (instance == null)                 // 2nd check, with the lock
                    instance = new Logger();
            }
        }
        return instance;
    }
    public synchronized void log(String msg) { System.out.println(++count + ": " + msg); }
}

// 3. Bill Pugh holder idiom - lazy, thread-safe, no synchronization cost
class Registry {
    private Registry() {}
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    public static Registry getInstance() { return Holder.INSTANCE; }
}

// 4. Enum singleton - safe even against reflection & serialization (Effective Java)
enum AppSettings { INSTANCE; String theme = "dark"; }

public class SingletonDemo {
    public static void main(String[] args) {
        Logger a = Logger.getInstance(), b = Logger.getInstance();
        a.log("start"); b.log("still the same logger");
        System.out.println(a == b);                   // true
        System.out.println(AppSettings.INSTANCE.theme);
    }
}

Factory (Factory Method) Lab 14

Intent: create objects without exposing the creation logic to the client. The client asks a factory for an object through a common interface, and the factory decides which concrete class to create. In the GoF Factory Method form, subclasses override a creation method.
Real-world uses: Calendar.getInstance(), NumberFormat.getInstance(), a JDBC DriverManager.getConnection, a notification service creating Email, SMS or Push senders, document editors creating different document types.

interface Notification { void send(String to, String msg); }
class EmailNotification implements Notification { public void send(String to, String m){ System.out.println("Email to " + to + ": " + m); } }
class SMSNotification   implements Notification { public void send(String to, String m){ System.out.println("SMS to " + to + ": " + m); } }
class PushNotification  implements Notification { public void send(String to, String m){ System.out.println("Push to " + to + ": " + m); } }

// Simple factory
class NotificationFactory {
    public static Notification create(String channel) {
        return switch (channel.toLowerCase()) {
            case "email" -> new EmailNotification();
            case "sms"   -> new SMSNotification();
            case "push"  -> new PushNotification();
            default -> throw new IllegalArgumentException("Unknown channel " + channel);
        };
    }
}

// GoF Factory Method: the creator defers creation to subclasses
abstract class Dialog {
    abstract Button createButton();                 // factory method
    void render() { Button b = createButton(); b.paint(); }   // uses the product without knowing its class
}
interface Button { void paint(); }
class WindowsDialog extends Dialog { Button createButton() { return () -> System.out.println("[Windows button]"); } }
class WebDialog     extends Dialog { Button createButton() { return () -> System.out.println("<html button>"); } }

public class FactoryDemo {
    public static void main(String[] args) {
        for (String ch : new String[]{"email", "sms", "push"})
            NotificationFactory.create(ch).send("asha", "Your order shipped");
        Dialog d = System.getProperty("os.name").startsWith("Windows") ? new WindowsDialog() : new WebDialog();
        d.render();
    }
}

Benefits: loose coupling (the client depends only on the interface), new products can be added in one place (Open/Closed), and creation logic is centralised.

Prototype

Intent: create new objects by cloning an existing instance (the prototype) instead of building them from scratch. This helps when creation is expensive (database loads, heavy setup) or when you need many similar objects with small differences.
Real-world uses: game enemies spawned from template objects, document templates, cell division, copying shapes in a drawing editor (Ctrl+C / Ctrl+V).

import java.util.*;

abstract class Shape implements Cloneable {
    String color; int x, y;
    abstract void draw();
    @Override public Shape clone() {
        try { return (Shape) super.clone(); } catch (CloneNotSupportedException e) { throw new AssertionError(); }
    }
}
class Circle extends Shape { int r; void draw(){ System.out.println(color + " circle r=" + r + " at " + x + "," + y); } }
class Rect   extends Shape { int w, h; void draw(){ System.out.println(color + " rect " + w + "x" + h + " at " + x + "," + y); } }

class ShapeRegistry {                                     // prototype registry
    private final Map<String, Shape> protos = new HashMap<>();
    void register(String key, Shape s) { protos.put(key, s); }
    Shape create(String key) { return protos.get(key).clone(); }
}

public class PrototypeDemo {
    public static void main(String[] args) {
        Circle big = new Circle(); big.r = 50; big.color = "red";
        Rect card = new Rect(); card.w = 85; card.h = 54; card.color = "blue";
        ShapeRegistry reg = new ShapeRegistry();
        reg.register("bigRedCircle", big); reg.register("card", card);

        Shape s1 = reg.create("bigRedCircle"); s1.x = 10;
        Shape s2 = reg.create("bigRedCircle"); s2.x = 99; s2.color = "green";
        s1.draw(); s2.draw(); big.draw();                 // prototype is unchanged
    }
}

Structural Patterns

Adapter

Intent: convert the interface of a class into another interface that clients expect, so classes with incompatible interfaces can work together. It is also called a wrapper.
Real-world analogy: a travel plug adapter, or a memory-card reader (SD card → USB). Java: Arrays.asList(), InputStreamReader (byte stream → character stream).

// Target interface our app uses
interface PaymentProcessor { void pay(double amountInRupees); }

// Existing third-party class with an incompatible API (we can't modify it)
class PayPalSDK {
    void makePayment(String currency, double amount) {
        System.out.println("PayPal charged " + currency + " " + String.format("%.2f", amount));
    }
}
// Adapter: implements the target, wraps the adaptee (object adapter via composition)
class PayPalAdapter implements PaymentProcessor {
    private final PayPalSDK paypal = new PayPalSDK();
    private static final double INR_PER_USD = 83.0;
    public void pay(double inr) { paypal.makePayment("USD", inr / INR_PER_USD); }   // translate the call
}
class UpiProcessor implements PaymentProcessor { public void pay(double inr){ System.out.println("UPI paid ₹" + inr); } }

public class AdapterDemo {
    static void checkout(PaymentProcessor p, double amt) { p.pay(amt); }   // client knows only the target
    public static void main(String[] args) {
        checkout(new UpiProcessor(), 830);
        checkout(new PayPalAdapter(), 830);
    }
}
Output

PayPal charged USD 10.00

Decorator

Intent: attach extra responsibilities to an object dynamically by wrapping it in decorator objects that share its interface. It is a flexible alternative to subclassing for extending behaviour, so you avoid a "class explosion" such as MilkSugarCoffee or WhipMilkCoffee.
Real-world uses: java.io: new BufferedReader(new InputStreamReader(new FileInputStream(f))), Collections.unmodifiableList, adding toppings to a pizza or coffee, middleware layers.

interface Coffee { String desc(); double cost(); }
class Espresso implements Coffee { public String desc(){ return "Espresso"; } public double cost(){ return 100; } }

abstract class CoffeeDecorator implements Coffee {         // has-a AND is-a Coffee
    protected final Coffee inner;
    CoffeeDecorator(Coffee c) { inner = c; }
}
class Milk extends CoffeeDecorator {
    Milk(Coffee c) { super(c); }
    public String desc() { return inner.desc() + " + Milk"; }
    public double cost() { return inner.cost() + 30; }
}
class Caramel extends CoffeeDecorator {
    Caramel(Coffee c) { super(c); }
    public String desc() { return inner.desc() + " + Caramel"; }
    public double cost() { return inner.cost() + 45; }
}
public class DecoratorDemo {
    public static void main(String[] args) {
        Coffee c = new Caramel(new Milk(new Milk(new Espresso())));   // stack decorators at runtime
        System.out.println(c.desc() + " = ₹" + c.cost());
    }
}

Facade

Intent: give a single simplified interface to a complex subsystem. Clients talk to the facade instead of to many subsystem classes, which lowers coupling.
Real-world uses: a home-theatre "Watch movie" button, a hotel reception desk, an "Order" API that coordinates inventory, payment and shipping, javax.faces.context.FacesContext, SLF4J.

class Inventory { boolean reserve(String item){ System.out.println("Reserved " + item); return true; } }
class Payment   { boolean charge(String user, double amt){ System.out.println("Charged " + user + " ₹" + amt); return true; } }
class Shipping  { String ship(String item, String addr){ System.out.println("Shipping " + item + " to " + addr); return "TRK123"; } }
class Notifier  { void email(String user, String m){ System.out.println("Email " + user + ": " + m); } }

class OrderFacade {                                        // the facade
    private final Inventory inv = new Inventory(); private final Payment pay = new Payment();
    private final Shipping ship = new Shipping();  private final Notifier note = new Notifier();
    public String placeOrder(String user, String item, double price, String addr) {
        if (!inv.reserve(item)) throw new IllegalStateException("Out of stock");
        if (!pay.charge(user, price)) throw new IllegalStateException("Payment failed");
        String trk = ship.ship(item, addr);
        note.email(user, "Order placed, tracking " + trk);
        return trk;
    }
}
public class FacadeDemo {
    public static void main(String[] args) {
        new OrderFacade().placeOrder("asha", "Laptop", 55000, "Delhi");  // one call, four subsystems
    }
}

Composite

Intent: arrange objects into tree structures for part–whole hierarchies, so clients treat individual objects (leaves) and groups (composites) the same way.
Real-world uses: file system (files and folders), GUI containers (a JavaFX Pane holds Nodes, which may themselves be Panes), organisation charts, menus and sub-menus.

import java.util.*;

interface FileSystemItem { long size(); void print(String indent); }

class FileItem implements FileSystemItem {                 // leaf
    private final String name; private final long size;
    FileItem(String n, long s) { name = n; size = s; }
    public long size() { return size; }
    public void print(String ind) { System.out.println(ind + "📄 " + name + " (" + size + " KB)"); }
}
class Folder implements FileSystemItem {                   // composite
    private final String name; private final List<FileSystemItem> children = new ArrayList<>();
    Folder(String n) { name = n; }
    Folder add(FileSystemItem i) { children.add(i); return this; }
    public long size() { return children.stream().mapToLong(FileSystemItem::size).sum(); }   // recursion
    public void print(String ind) {
        System.out.println(ind + "📁 " + name + " (" + size() + " KB)");
        for (FileSystemItem c : children) c.print(ind + "   ");
    }
}
public class CompositeDemo {
    public static void main(String[] args) {
        Folder root = new Folder("root")
            .add(new FileItem("notes.txt", 4))
            .add(new Folder("src").add(new FileItem("Main.java", 12)).add(new FileItem("Util.java", 8)))
            .add(new Folder("img").add(new FileItem("logo.png", 120)));
        root.print("");                                     // same call on leaf or composite
    }
}
Output
📁 root (144 KB)
   📄 notes.txt (4 KB)
   📁 src (20 KB)
      📄 Main.java (12 KB)
      📄 Util.java (8 KB)
   📁 img (120 KB)
      📄 logo.png (120 KB)

Proxy

Intent: provide a surrogate or placeholder that controls access to another object. It has the same interface as the real object. Kinds: virtual proxy (lazy loading of expensive objects), protection proxy (access control), remote proxy (RMI stub), caching / logging proxy.
Real-world uses: a cheque or debit card as a proxy for a bank account, Hibernate lazy loading, Spring AOP, image placeholders in documents.

interface Image { void display(); }

class HighResImage implements Image {
    private final String file;
    HighResImage(String f) { file = f; System.out.println("Loading " + f + " from disk (slow)..."); }
    public void display() { System.out.println("Displaying " + file); }
}
class ImageProxy implements Image {                         // virtual + protection proxy
    private final String file; private final String role;
    private HighResImage real;                              // created only when needed
    ImageProxy(String f, String role) { file = f; this.role = role; }
    public void display() {
        if (!role.equals("member")) { System.out.println("Access denied for " + file); return; }
        if (real == null) real = new HighResImage(file);    // lazy load
        real.display();
    }
}
public class ProxyDemo {
    public static void main(String[] args) {
        Image img = new ImageProxy("photo.png", "member");
        System.out.println("Proxy created (nothing loaded yet)");
        img.display();                                      // loads now
        img.display();                                      // cached, no reload
        new ImageProxy("secret.png", "guest").display();
    }
}

Flyweight

Intent: share fine-grained objects so that large numbers of them can be supported efficiently. Split the state into intrinsic state (shared, immutable, stored in the flyweight) and extrinsic state (context-specific, passed in by the client). A factory caches and reuses flyweights.
Real-world uses: characters in a text editor (one glyph object per character, while position is extrinsic), trees in a game forest, Integer.valueOf(-128..127) cache, the String pool.

import java.util.*;

final class TreeType {                                      // flyweight: intrinsic, shared, immutable
    final String name, color, texture;
    TreeType(String n, String c, String t) { name = n; color = c; texture = t; }
    void draw(int x, int y) { System.out.println(name + "(" + color + ") at " + x + "," + y); }
}
class TreeFactory {
    private static final Map<String, TreeType> cache = new HashMap<>();
    static TreeType get(String n, String c, String t) {
        return cache.computeIfAbsent(n + c + t, k -> { System.out.println("  new TreeType " + n); return new TreeType(n, c, t); });
    }
    static int count() { return cache.size(); }
}
record Tree(int x, int y, TreeType type) {                  // extrinsic state (x, y) per tree
    void draw() { type.draw(x, y); }
}
public class FlyweightDemo {
    public static void main(String[] args) {
        List<Tree> forest = new ArrayList<>();
        Random r = new Random(1);
        for (int i = 0; i < 1_000_000; i++) {
            TreeType t = (i % 2 == 0) ? TreeFactory.get("Oak", "green", "oak.png") : TreeFactory.get("Pine", "dark", "pine.png");
            forest.add(new Tree(r.nextInt(1000), r.nextInt(1000), t));
        }
        forest.get(0).draw();
        System.out.println(forest.size() + " trees share only " + TreeFactory.count() + " TreeType objects");
        Integer a = 127, b = 127, c = 128, d = 128;
        System.out.println((a == b) + " " + (c == d));      // true false  (JDK flyweight cache)
    }
}

Behavioural Patterns

Iterator

Intent: access the elements of a collection one after another without exposing its internal representation (array, linked list, tree). Java's java.util.Iterator (hasNext(), next(), remove()) and Iterable (which enables the for-each loop) are this pattern.

import java.util.*;

class Playlist implements Iterable<String> {
    private final String[] songs; private int count;
    Playlist(int cap) { songs = new String[cap]; }
    void add(String s) { songs[count++] = s; }

    @Override public Iterator<String> iterator() {          // the client never sees the array
        return new Iterator<>() {
            private int i = 0;
            public boolean hasNext() { return i < count; }
            public String next() {
                if (!hasNext()) throw new NoSuchElementException();
                return songs[i++];
            }
        };
    }
    Iterator<String> reverseIterator() {                    // several traversal strategies
        return new Iterator<>() {
            int i = count - 1;
            public boolean hasNext() { return i >= 0; }
            public String next() { return songs[i--]; }
        };
    }
}
public class IteratorDemo {
    public static void main(String[] args) {
        Playlist p = new Playlist(10);
        p.add("Song A"); p.add("Song B"); p.add("Song C");
        for (String s : p) System.out.println("▶ " + s);     // for-each uses iterator()
        Iterator<String> rev = p.reverseIterator();
        while (rev.hasNext()) System.out.println("◀ " + rev.next());
    }
}

Strategy

Intent: define a family of algorithms, put each one in its own class, and make them interchangeable at runtime. The context holds a reference to a strategy interface instead of hard-coding if/else branches.
Real-world uses: Comparator passed to sort(), payment methods, compression algorithms (zip/rar), route planning (car/walk/bus), discount rules.

interface DiscountStrategy { double apply(double amount); }

class NoDiscount      implements DiscountStrategy { public double apply(double a) { return a; } }
class PercentDiscount implements DiscountStrategy {
    private final double pct; PercentDiscount(double p) { pct = p; }
    public double apply(double a) { return a * (1 - pct / 100); }
}
class FlatDiscount implements DiscountStrategy {
    private final double off; FlatDiscount(double o) { off = o; }
    public double apply(double a) { return Math.max(0, a - off); }
}
class ShoppingCart {                                       // context
    private DiscountStrategy strategy = new NoDiscount();
    void setStrategy(DiscountStrategy s) { strategy = s; } // swap at runtime
    double checkout(double total) { return strategy.apply(total); }
}
public class StrategyDemo {
    public static void main(String[] args) {
        ShoppingCart cart = new ShoppingCart();
        System.out.println(cart.checkout(1000));                          // 1000.0
        cart.setStrategy(new PercentDiscount(10)); System.out.println(cart.checkout(1000)); // 900.0
        cart.setStrategy(new FlatDiscount(250));   System.out.println(cart.checkout(1000)); // 750.0
        cart.setStrategy(a -> a > 500 ? a - 100 : a);  System.out.println(cart.checkout(1000)); // lambda strategy: 900.0
    }
}

Template Method

Intent: define the skeleton of an algorithm in a base-class method (often final), and let subclasses override specific steps without changing the overall structure. This is the "Hollywood principle": don't call us, we'll call you.
Real-world uses: AbstractList (you give get and size), HttpServlet.service() calling doGet/doPost, JUnit's setUp/test/tearDown, data importers (open → parse → validate → save).

abstract class DataImporter {
    public final void importData(String src) {       // template method: fixed order
        String raw = read(src);
        var records = parse(raw);
        if (validate(records)) save(records);
        hook();
    }
    protected String read(String src) { System.out.println("Reading " + src); return "a,b;c,d"; }
    protected abstract java.util.List<String> parse(String raw);   // varies
    protected boolean validate(java.util.List<String> r) { return !r.isEmpty(); }
    protected void save(java.util.List<String> r) { System.out.println("Saved " + r); }
    protected void hook() {}                          // optional hook (empty by default)
}
class CsvImporter extends DataImporter {
    protected java.util.List<String> parse(String raw) { return java.util.List.of(raw.split(";")); }
}
class JsonImporter extends DataImporter {
    protected java.util.List<String> parse(String raw) { return java.util.List.of("{" + raw + "}"); }
    @Override protected void hook() { System.out.println("JSON import audited"); }
}
public class TemplateDemo {
    public static void main(String[] args) {
        new CsvImporter().importData("data.csv");
        new JsonImporter().importData("data.json");
    }
}

Observer Lab 14

Intent: define a one-to-many dependency so that when one object (the subject or publisher) changes state, all its observers (subscribers) are notified automatically. Publisher and subscribers stay loosely coupled.
Real-world uses: YouTube channel subscriptions, newsletters, stock price tickers, GUI event listeners (JavaFX button.setOnAction), MVC (the model notifies views), PropertyChangeListener.

import java.util.*;

interface Observer { void update(String stock, double price); }

interface Subject {
    void subscribe(Observer o);
    void unsubscribe(Observer o);
    void notifyObservers();
}
class StockTicker implements Subject {
    private final List<Observer> observers = new ArrayList<>();
    private String stock; private double price;

    public void subscribe(Observer o)   { observers.add(o); }
    public void unsubscribe(Observer o) { observers.remove(o); }
    public void notifyObservers()       { for (Observer o : observers) o.update(stock, price); }

    public void setPrice(String stock, double price) {      // state change → notify
        this.stock = stock; this.price = price;
        notifyObservers();
    }
}
class MobileApp implements Observer {
    private final String user; MobileApp(String u) { user = u; }
    public void update(String s, double p) { System.out.println("📱 " + user + ": " + s + " is now ₹" + p); }
}
class TradingBot implements Observer {
    public void update(String s, double p) { if (p < 1500) System.out.println("🤖 Bot: BUY " + s + " at " + p); }
}
public class ObserverDemo {
    public static void main(String[] args) {
        StockTicker ticker = new StockTicker();
        Observer asha = new MobileApp("Asha"), bot = new TradingBot();
        ticker.subscribe(asha); ticker.subscribe(bot);
        ticker.setPrice("INFY", 1550);
        ticker.setPrice("INFY", 1480);
        ticker.unsubscribe(asha);
        ticker.setPrice("INFY", 1450);
    }
}
Output
📱 Asha: INFY is now ₹1550.0
📱 Asha: INFY is now ₹1480.0
🤖 Bot: BUY INFY at 1480.0
🤖 Bot: BUY INFY at 1450.0

State

Intent: let an object change its behaviour when its internal state changes, so it looks as if the object changed its class. Each state is its own class implementing a common interface, and the context delegates to its current state object. This replaces large switch(state) blocks.
Real-world uses: vending machine, traffic light, order lifecycle (New → Paid → Shipped → Delivered), TCP connection, media player (Playing/Paused/Stopped), document workflow.

interface OrderState {
    void next(Order o);
    void cancel(Order o);
    String name();
}
class NewState implements OrderState {
    public void next(Order o)   { System.out.println("Payment received"); o.setState(new PaidState()); }
    public void cancel(Order o) { System.out.println("Order cancelled");  o.setState(new CancelledState()); }
    public String name() { return "NEW"; }
}
class PaidState implements OrderState {
    public void next(Order o)   { System.out.println("Order shipped");    o.setState(new ShippedState()); }
    public void cancel(Order o) { System.out.println("Refund issued");    o.setState(new CancelledState()); }
    public String name() { return "PAID"; }
}
class ShippedState implements OrderState {
    public void next(Order o)   { System.out.println("Order delivered");  o.setState(new DeliveredState()); }
    public void cancel(Order o) { System.out.println("Cannot cancel - already shipped"); }
    public String name() { return "SHIPPED"; }
}
class DeliveredState implements OrderState {
    public void next(Order o)   { System.out.println("Already delivered"); }
    public void cancel(Order o) { System.out.println("Use return process"); }
    public String name() { return "DELIVERED"; }
}
class CancelledState implements OrderState {
    public void next(Order o)   { System.out.println("Order is cancelled"); }
    public void cancel(Order o) { System.out.println("Already cancelled"); }
    public String name() { return "CANCELLED"; }
}
class Order {                                              // context
    private OrderState state = new NewState();
    void setState(OrderState s) { state = s; }
    void next()   { state.next(this); }                    // delegate to current state
    void cancel() { state.cancel(this); }
    String status() { return state.name(); }
}
public class StateDemo {
    public static void main(String[] args) {
        Order o = new Order();
        o.next(); o.next(); o.cancel(); o.next();
        System.out.println("Final: " + o.status());
    }
}
Output
Payment received
Order shipped
Cannot cancel - already shipped
Order delivered
Final: DELIVERED

State vs Strategy: they have the same structure. In Strategy the client picks the algorithm and strategies don't know about each other. In State, the states themselves trigger transitions to other states.

Chain of Responsibility

Intent: pass a request along a chain of handlers. Each handler either processes the request or forwards it to the next one. This decouples the sender from the receivers.
Real-world uses: customer-support escalation (bot → agent → manager), expense approvals by amount, servlet filters and middleware, exception propagation up the call stack, logging levels, JavaFX event bubbling.

abstract class Approver {
    private Approver next;
    Approver setNext(Approver n) { next = n; return n; }    // returns n for fluent chaining
    void approve(String item, double amt) {
        if (canApprove(amt)) System.out.println(getClass().getSimpleName() + " approved " + item + " ₹" + amt);
        else if (next != null) next.approve(item, amt);       // pass along
        else System.out.println("Nobody can approve " + item + " ₹" + amt);
    }
    protected abstract boolean canApprove(double amt);
}
class TeamLead extends Approver { protected boolean canApprove(double a) { return a <= 10_000; } }
class Manager  extends Approver { protected boolean canApprove(double a) { return a <= 50_000; } }
class Director extends Approver { protected boolean canApprove(double a) { return a <= 2_00_000; } }

public class ChainDemo {
    public static void main(String[] args) {
        Approver chain = new TeamLead();
        chain.setNext(new Manager()).setNext(new Director());
        chain.approve("Mouse", 1500);
        chain.approve("Laptop", 45000);
        chain.approve("Server", 150000);
        chain.approve("Building", 9_00_00_000);
    }
}
Output
TeamLead approved Mouse ₹1500.0
Manager approved Laptop ₹45000.0
Director approved Server ₹150000.0
Nobody can approve Building ₹9.0E7
