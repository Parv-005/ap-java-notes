Polymorphism using Inheritance PYQ ES24-1aPYQ MS24-4aPYQ MS25-5bPYQ EJ26-2aPYQ MS26-4aLab 5

Polymorphism (Greek for "many forms") is the ability of one name (a method or reference) to behave differently depending on context. Java has two kinds:

Compile-time (static) polymorphismRuntime (dynamic) polymorphism
Achieved byMethod overloading (and constructor overloading)Method overriding + upcasting
Resolved byCompiler, using the reference type and argument typesJVM at runtime, using the actual object type
BindingEarly / static bindingLate / dynamic binding (dynamic method dispatch)
Inheritance needed?NoYes (or an interface)
SpeedSlightly fasterVirtual-call lookup (optimised by the JIT)
Applies tostatic, private, final methods are always static-boundInstance, non-final, non-private methods

Why polymorphism matters (MS24-4a): you write general code (for (Shape s : shapes) s.area()) that works with types that don't exist yet. It removes long if/else instanceof chains, makes the code extensible (Open/Closed Principle) and loosely coupled, and it is the basis of most design patterns (Strategy, State, Template, Observer).

Lab 5: Shape → Circle, Square, Triangle, showing overriding AND overloading
abstract class Shape {
    abstract double area();                                  // to be overridden
    void describe() { System.out.printf("%s with area %.2f%n", getClass().getSimpleName(), area()); }
}
class Circle extends Shape {
    double r; Circle(double r){ this.r = r; }
    @Override double area() { return Math.PI * r * r; }      // OVERRIDING
}
class Square extends Shape {
    double s; Square(double s){ this.s = s; }
    @Override double area() { return s * s; }
}
class Triangle extends Shape {
    double b, h; Triangle(double b, double h){ this.b = b; this.h = h; }
    @Override double area() { return 0.5 * b * h; }
}

class AreaCalculator {                                       // OVERLOADING: same name, different params
    static double area(double r)              { return Math.PI * r * r; }      // circle
    static double area(int side)              { return side * side; }          // square
    static double area(double b, double h)    { return 0.5 * b * h; }          // triangle
    static double area(double a, double b, double c) {                         // triangle by Heron
        double s = (a + b + c) / 2;
        return Math.sqrt(s * (s - a) * (s - b) * (s - c));
    }
}

public class PolyDemo {
    public static void main(String[] args) {
        // Runtime polymorphism: reference type Shape, object types vary
        Shape[] shapes = { new Circle(1), new Square(2), new Triangle(3, 4) };
        for (Shape s : shapes) s.describe();          // JVM picks the area() of each actual class

        // Compile-time polymorphism: compiler picks the overload by argument list
        System.out.println(AreaCalculator.area(1.0));         // double → circle
        System.out.println(AreaCalculator.area(2));           // int → square
        System.out.println(AreaCalculator.area(3.0, 4.0));    // two doubles → triangle
        System.out.println(AreaCalculator.area(3, 4, 5));     // three → Heron = 6.0
    }
}

Overloading with different numbers or types of parameters (MS26-4a):

class Printer {
    void print(int x)            { System.out.println("int: " + x); }
    void print(double x)         { System.out.println("double: " + x); }
    void print(String s)         { System.out.println("String: " + s); }
    void print(String s, int n)  { System.out.println((s + " ").repeat(n)); }
    void print(int n, String s)  { System.out.println(n + ":" + s); }   // order differs
    void print(int... xs)        { System.out.println("varargs: " + xs.length); }
}
// p.print(5) → int; p.print(5L) → widened to double; p.print('a') → char widened to int: 97
// p.print() → varargs: 0

Overload resolution order (the compiler tries each phase in turn): ① exact match or widening of primitives → ② boxing/unboxing → ③ varargs. If two methods match equally well, the call is ambiguous and won't compile.

Method Resolution PYQ ES24-2cPYQ EJ26-2aPYQ MJ26-4aPYQ MS26-3a

Method resolution is how Java decides which method body runs for a call like ref.m(args). It happens in two phases:

Phase 1: Compile time (choosing the signature)

  1. The compiler looks at the declared (static) type of the reference.
  2. It finds all accessible methods named m in that type and its supertypes.
  3. It picks the most specific overload for the argument types (overload resolution).
  4. If the reference type has no matching method, the result is a compile error, even if the real object has it.
  5. It writes the chosen signature into the bytecode (for example invokevirtual Animal.sound()V).

Phase 2: Runtime (choosing the implementation): dynamic method dispatch

  1. The JVM looks at the actual class of the object the reference points to.
  2. It searches that class for a method with the chosen signature. If it is there, that body runs.
  3. Otherwise it walks up the inheritance chain (parent, grandparent, … Object) and runs the first match it finds.
  4. In practice the JVM uses a per-class virtual method table (vtable), so the lookup is a fast index operation.

Exceptions to dynamic dispatch: static, private, final methods and constructors are bound at compile time (invokestatic / invokespecial). Fields are never polymorphic: field access always uses the reference type.

class Person {
    String role = "person";
    void work()           { System.out.println("Person works"); }
    void intro()          { System.out.println("I am a person"); work(); }   // calls the overridden work()!
    static void species() { System.out.println("Homo sapiens (Person)"); }
}
class Employee extends Person {
    String role = "employee";
    @Override void work() { System.out.println("Employee writes code"); }
    static void species() { System.out.println("Homo sapiens (Employee)"); } // HIDING, not overriding
}
class Manager extends Employee {
    @Override void work() {
        super.work();                              // explicitly call the parent version
        System.out.println("Manager reviews code");
    }
    void approve() { System.out.println("approved"); }
}
public class Resolution {
    public static void main(String[] args) {
        Person p = new Manager();       // reference type Person, object type Manager
        p.work();                       // runtime: Manager.work → super → Employee.work
        p.intro();                      // intro() inherited from Person, but work() → Manager's
        p.species();                    // static → reference type → Person's version
        System.out.println(p.role);     // field → reference type → "person"
        // p.approve();                 // compile error: Person has no approve()
        ((Manager) p).approve();        // downcast first
    }
}

The role of super: super.work() is not dynamically dispatched. It always calls the direct parent's version (invokespecial). That's how a subclass extends behaviour instead of replacing it.

Prefer an interface when: unrelated classes share a capability (Comparable, Payable). You need multiple inheritance of type. You want to define an API that different teams or vendors implement. You want to swap implementations or mock them in tests.
Prefer inheritance (abstract class) when: classes are closely related and share state and code, you need constructors or non-public members, or you want a Template Method skeleton.

A design that needs both (EJ26-1c): a payroll system. All employees share state (id, name, base salary) and a salary-calculation skeleton, so that belongs in an abstract class. But only some employees are Taxable, and both employees and vendors are Payable. Those capabilities cut across the hierarchy, so they belong in interfaces. One mechanism alone isn't enough. With only an abstract class, Vendor (not an employee) couldn't be paid by the same code, and Java can't extend two classes. With only interfaces, each employee type would repeat the shared fields and constructor logic.

interface Payable  { double amountDue(); }
interface Taxable  { default double tax() { return 0.1 * taxableIncome(); } double taxableIncome(); }

abstract class Employee implements Payable {                  // shared state + skeleton
    protected final int id; protected final String name; protected final double base;
    Employee(int id, String name, double base) { this.id = id; this.name = name; this.base = base; }
    protected abstract double bonus();                        // varies
    public final double amountDue() { return base + bonus(); }// fixed algorithm (template)
}
class Engineer extends Employee implements Taxable {
    Engineer(int id, String n, double b) { super(id, n, b); }
    protected double bonus() { return 0.2 * base; }
    public double taxableIncome() { return amountDue(); }
}
class Intern extends Employee {                                // not taxable
    Intern(int id, String n) { super(id, n, 15000); }
    protected double bonus() { return 0; }
}
class Vendor implements Payable, Taxable {                    // NOT an Employee
    double invoice; Vendor(double inv) { invoice = inv; }
    public double amountDue() { return invoice; }
    public double taxableIncome() { return invoice; }
}
public class Payroll {
    public static void main(String[] args) {
        List<Payable> toPay = List.of(new Engineer(1, "Riya", 80000), new Intern(2, "Sam"), new Vendor(50000));
        for (Payable p : toPay) {
            System.out.printf("%-8s pay=%.0f", p.getClass().getSimpleName(), p.amountDue());
            if (p instanceof Taxable t) System.out.printf("  tax=%.0f", t.tax());
            System.out.println();
        }
    }
}
Output
Engineer pay=96000  tax=9600
Intern   pay=15000
Vendor   pay=50000  tax=5000

Constructor Invocation in the Inheritance Tree PYQ MJ26-4a

When you create a subclass object, constructors run from the top of the hierarchy down: Object → grandparent → parent → child. The parent part of an object must be fully set up before the child part uses it.

  • The first statement of every constructor is either this(...) or super(...). If you write neither, the compiler inserts super() (no-arg).
  • So if the parent has no no-arg constructor, the child must call super(args) explicitly, or it won't compile.
  • Full order for new C(): static initialisers (on first class load, parent first) → for each level from the top down: instance field initialisers and instance blocks, then the constructor body.
class Person {
    static { System.out.println("1. Person static block (class load)"); }
    { System.out.println("3. Person instance block"); }
    Person() { System.out.println("4. Person constructor"); }
    void role() { System.out.println("Person"); }
}
class Employee extends Person {
    static { System.out.println("2. Employee static block"); }
    Employee() { super(); System.out.println("5. Employee constructor"); }   // super() implicit anyway
    @Override void role() { System.out.println("Employee"); }
}
class Manager extends Employee {
    String dept;
    Manager(String dept) {                   // implicit super() → Employee()
        this.dept = dept;
        System.out.println("6. Manager constructor (" + dept + ")");
    }
    @Override void role() { System.out.println("Manager of " + dept); }
}
public class ChainDemo {
    public static void main(String[] args) {
        Manager m = new Manager("Sales");
        m.role();                            // method resolution: most-derived → Manager.role
    }
}

Abstract Classes PYQ MS24-5bPYQ ES25-1a(i)Lab 7

An abstract class is a class declared with abstract that can't be instantiated. It represents a general concept (Shape, Animal, Employee) that is only partly defined. It may contain abstract methods (declared without a body, ending in ;), which every concrete subclass must override, as well as normal methods, fields and constructors.

// Syntax
access abstract class ClassName {
    // fields, constructors, concrete methods
    access abstract returnType methodName(params);   // no body
}
  • If a class has even one abstract method, the class must be abstract.
  • An abstract class may have zero abstract methods (only to prevent instantiation).
  • It can have constructors. They run when a subclass is created, via super().
  • A subclass that doesn't implement every abstract method must itself be abstract.
  • A reference of the abstract type is allowed: Shape s = new Circle();

Can an abstract method be private? No. An abstract method has to be overridden by a subclass, but private methods aren't visible to subclasses, so they can never be overridden. private abstract is a contradiction and a compile error ("illegal combination of modifiers"). For the same reason, abstract methods can't be final (can't be overridden) or static (static methods aren't dispatched by object). They can be public, protected or default.

Lab 7: Abstraction with abstract class + interface as a contract
interface Operation {                         // contract: what every operation must offer
    double apply(double a, double b);
    String symbol();
}
abstract class BaseOperation implements Operation {   // partial implementation
    private static int count = 0;
    protected BaseOperation() { count++; }
    public void show(double a, double b) {    // concrete, shared
        System.out.println(a + " " + symbol() + " " + b + " = " + apply(a, b));
    }
    static int count() { return count; }
}
class Add extends BaseOperation { public double apply(double a,double b){return a+b;} public String symbol(){return "+";} }
class Mul extends BaseOperation { public double apply(double a,double b){return a*b;} public String symbol(){return "×";} }
class Pow extends BaseOperation { public double apply(double a,double b){return Math.pow(a,b);} public String symbol(){return "^";} }

public class AbstractionDemo {
    public static void main(String[] args) {
        // BaseOperation op = new BaseOperation();   // ERROR: abstract, cannot instantiate
        BaseOperation[] ops = { new Add(), new Mul(), new Pow() };
        for (BaseOperation op : ops) op.show(2, 5);
        System.out.println("Operations created: " + BaseOperation.count());
    }
}
Output
2.0 + 5.0 = 7.0
2.0 × 5.0 = 10.0
2.0 ^ 5.0 = 32.0

Immutable Classes PYQ MS24-5aPYQ MJ26-4bPYQ MS26-5a

An immutable object's state can't change after it is constructed. Every "modifying" operation returns a new object. Examples: String, wrapper classes (Integer, Double), LocalDate, BigDecimal, List.of(...).

Rules for creating an immutable class

  1. Declare the class final, so subclasses can't add mutable behaviour or override methods.
  2. Make all fields private final.
  3. Provide no setters and no methods that change state.
  4. Initialise all fields in the constructor.
  5. Defensive copy on input: if a constructor argument is mutable (Date, array, List), store a copy, not the caller's reference.
  6. Defensive copy on output: getters return a copy or an unmodifiable view of mutable fields.
  7. "Modifier" methods (withers) return a new instance.
import java.util.*;

public final class ImmutableStudent {                       // rule 1
    private final int roll;                                 // rule 2
    private final String name;                              // String is already immutable
    private final Date dob;                                 // mutable type!
    private final List<Integer> marks;                      // mutable type!

    public ImmutableStudent(int roll, String name, Date dob, List<Integer> marks) {
        this.roll  = roll;
        this.name  = Objects.requireNonNull(name);
        this.dob   = new Date(dob.getTime());               // rule 5: deep/defensive copy IN
        this.marks = List.copyOf(marks);                    // unmodifiable copy
    }
    public int getRoll()          { return roll; }
    public String getName()       { return name; }
    public Date getDob()          { return new Date(dob.getTime()); }   // rule 6: copy OUT
    public List<Integer> getMarks(){ return marks; }                     // already unmodifiable

    public ImmutableStudent withName(String newName) {       // rule 7
        return new ImmutableStudent(roll, newName, dob, marks);
    }
    @Override public String toString() { return roll + " " + name + " " + dob + " " + marks; }

    public static void main(String[] args) {
        Date d = new Date(100, 0, 1);
        List<Integer> m = new ArrayList<>(List.of(90, 85));
        ImmutableStudent s = new ImmutableStudent(1, "Asha", d, m);

        d.setYear(50); m.add(0);               // try to mutate through the original references
        s.getDob().setYear(10);                // try to mutate through the getter
        try { s.getMarks().add(1); } catch (UnsupportedOperationException e) { System.out.println("marks are read-only"); }

        System.out.println(s);                 // unchanged: year 2000, [90, 85]
        ImmutableStudent s2 = s.withName("Asha K");
        System.out.println(s == s2);           // false - a new object
    }
}

Without defensive copying (this.dob = dob;), the caller's later d.setYear(50) would change the "immutable" student. This is exactly what MS26-5a asks about. Shallow vs deep copy matters here: for a list of mutable objects, you must copy the elements too. See cloning.

Java 16+ record gives you final private fields, a constructor, accessors, equals/hashCode/toString automatically: public record Point(int x, int y) {}. You still have to copy mutable components yourself in a compact constructor.

Advantages: automatically thread-safe (no synchronisation needed); safe to share and cache (the String pool); safe as HashMap keys, since the hashCode never changes; simpler to reason about; protects against unwanted changes (security). Disadvantage: a new object for every change, which can mean extra garbage. StringBuilder is the mutable companion of String.

The Object Class PYQ MS26-1b

java.lang.Object is the root of the class hierarchy. Every class extends it directly or indirectly, even if you don't write extends. So an Object reference can hold anything (arrays too), and every object has these methods:

MethodPurpose / default behaviour
String toString()Text form. Default: ClassName@hexHashCode. Override for readable output. Called automatically by println and string concatenation.
boolean equals(Object o)Logical equality. Default: same as == (reference identity).
int hashCode()Integer hash used by HashMap and HashSet. Must be consistent with equals.
Class<?> getClass()Runtime class object (reflection). final, so it can't be overridden.
Object clone()protected. Field-by-field (shallow) copy. Needs Cloneable.
void finalize()Called before GC. Deprecated.
wait(), notify(), notifyAll()Thread coordination on the object's monitor. See Unit 5.
import java.util.Objects;

public class Point implements Cloneable {
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }

    @Override public String toString() { return "Point(" + x + ", " + y + ")"; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;                       // same reference
        if (!(o instanceof Point)) return false;          // null-safe type check
        Point p = (Point) o;
        return x == p.x && y == p.y;                      // compare significant fields
    }
    @Override public int hashCode() { return Objects.hash(x, y); }

    @Override public Point clone() {
        try { return (Point) super.clone(); }
        catch (CloneNotSupportedException e) { throw new AssertionError(); }
    }

    public static void main(String[] args) {
        Point a = new Point(1, 2), b = new Point(1, 2);
        System.out.println(a);                         // Point(1, 2)  (toString)
        System.out.println(a == b);                    // false        (different objects)
        System.out.println(a.equals(b));               // true         (same content)
        System.out.println(a.hashCode() == b.hashCode()); // true      (contract)
        System.out.println(a.getClass().getName());    // Point
        Point c = a.clone();
        System.out.println(c.equals(a) + " " + (c != a)); // true true
    }
}

Comparing Objects: == vs equals() PYQ MS26-3b

== operatorequals() method
For primitives: compares values. For objects: compares references (same memory location?)Compares contents / logical equality, if overridden
An operator, can't be overriddenA method of Object, can be overridden
Works with null on either sidenull.equals(x) throws NullPointerException
public class StringCompare {
    public static void main(String[] args) {
        String s1 = "Java";                 // string literal → String Constant Pool
        String s2 = "Java";                 // reuses the same pooled object
        String s3 = new String("Java");     // new object on the heap
        String s4 = s3.intern();            // pooled version

        System.out.println(s1 == s2);       // true  - same pooled reference
        System.out.println(s1 == s3);       // false - different objects
        System.out.println(s1.equals(s3));  // true  - same characters
        System.out.println(s1 == s4);       // true  - intern() returns the pooled one
        System.out.println("JAVA".equalsIgnoreCase(s1)); // true
    }
}

Explanation: literals are stored once in the String pool, so s1 and s2 share a reference. new String always makes a new heap object, so == is false while equals (overridden in String to compare characters) is true. Always compare strings with equals().

The equals() and hashCode() contract

  • Reflexive: x.equals(x) is true. Symmetric: x.equals(y) ⇔ y.equals(x). Transitive. Consistent (same result on repeated calls). x.equals(null) is false.
  • If a.equals(b), then a.hashCode() == b.hashCode() must hold. The reverse isn't required (collisions are allowed).
  • If you override equals but not hashCode, a HashSet will keep "duplicates" and HashMap.get() fails.

Comparable Interface PYQ ES24-1bPYQ EJ26-2cPYQ MS26-5b

java.lang.Comparable<T> defines the natural ordering of a class. The class itself implements one method:

public interface Comparable<T> { int compareTo(T other); }

Working of compareTo: it returns a negative number if this < other, zero if they are equal, and positive if this > other. Collections.sort(list), Arrays.sort, TreeSet and TreeMap call it to order elements. It should be consistent with equals.

import java.util.*;

class Student implements Comparable<Student> {
    int roll; String name; double marks;
    Student(int r, String n, double m) { roll = r; name = n; marks = m; }

    @Override
    public int compareTo(Student o) {
        return Double.compare(this.marks, o.marks);   // ascending by marks
        // avoid "return (int)(this.marks - o.marks)" - truncation/overflow bugs
    }
    @Override public String toString() { return name + "(" + marks + ")"; }
}
public class ComparableDemo {
    public static void main(String[] args) {
        List<Student> list = new ArrayList<>(List.of(
            new Student(3, "Ravi", 72.5), new Student(1, "Asha", 91),
            new Student(2, "Kiran", 85), new Student(4, "Meena", 72.5)));
        Collections.sort(list);                       // uses compareTo
        System.out.println("By marks ↑ : " + list);
        list.sort(Collections.reverseOrder());        // reverse natural order
        System.out.println("By marks ↓ : " + list);
    }
}
Output
By marks ↑ : [Ravi(72.5), Meena(72.5), Kiran(85.0), Asha(91.0)]
By marks ↓ : [Asha(91.0), Kiran(85.0), Ravi(72.5), Meena(72.5)]

Output explained: Collections.sort repeatedly calls a.compareTo(b). Ravi and Meena compare as 0 (equal). The sort is stable, so they keep their original relative order.

Comparator Interface PYQ ES24-1bPYQ EJ26-2c

java.util.Comparator<T> defines an external, custom ordering in a separate object. You can have many comparators for one class, and you can sort classes you can't modify.

public interface Comparator<T> { int compare(T a, T b); /* + many default helpers */ }
import java.util.*;

class Student {
    int roll; String name; String dept; double marks;
    Student(int r, String n, String d, double m) { roll = r; name = n; dept = d; marks = m; }
    public String getName() { return name; }  public String getDept() { return dept; }
    public double getMarks() { return marks; } public int getRoll() { return roll; }
    @Override public String toString() { return String.format("%-6s %-3s %5.1f #%d", name, dept, marks, roll); }
}

// 1. Classic: separate class
class NameComparator implements Comparator<Student> {
    public int compare(Student a, Student b) { return a.name.compareTo(b.name); }
}

public class ComparatorDemo {
    public static void main(String[] args) {
        List<Student> list = new ArrayList<>(List.of(
            new Student(3, "Ravi", "CSE", 72.5), new Student(1, "Asha", "IT", 91),
            new Student(2, "Kiran", "IT", 85),   new Student(4, "Meena", "CSE", 72.5),
            new Student(5, "Arjun", "IT", 85)));

        list.sort(new NameComparator());
        System.out.println("By name:\n" + String.join("\n", list.stream().map(Object::toString).toList()));

        // 2. Anonymous class
        list.sort(new Comparator<Student>() {
            public int compare(Student a, Student b) { return Integer.compare(a.roll, b.roll); }
        });

        // 3. Lambda
        list.sort((a, b) -> Double.compare(b.marks, a.marks));   // marks descending

        // 4. MULTIPLE ATTRIBUTES: dept ↑, then marks ↓, then name ↑   (EJ26-2c)
        Comparator<Student> multi = Comparator.comparing(Student::getDept)
                .thenComparing(Student::getMarks, Comparator.reverseOrder())
                .thenComparing(Student::getName);
        list.sort(multi);
        System.out.println("\nBy dept ↑, marks ↓, name ↑:");
        list.forEach(System.out::println);
    }
}
Output
By name:
Arjun  IT   85.0 #5
Asha   IT   91.0 #1
Kiran  IT   85.0 #2
